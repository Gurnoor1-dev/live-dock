# Infinite Flight: PublicApi v3 (OAuth2)

> Full reference for Infinite Flight PublicApi v3 (also called Live API v3), the OAuth2 HTTP API for third-party apps. It reads the public Live data (sessions, flights, ATC, users, aircraft, and airports) with a user token or a server-to-server token, and the Live organizations, members, aircraft, flight logs, and schedules of the signed-in user. For developers and AI agents that build apps, websites, and bots on Infinite Flight data.

Source: https://infiniteflight.com/guide/developer-reference/live-api-v3 (infiniteflight-docs ae80275). Generated by a model on 2026-11-12. If this file and the website disagree, the website is correct.

Simulated flight data only. Not for real-world aviation use.

PublicApi v3 is the default API for new apps. The Live API v2 (API key, `https://api.infiniteflight.com/public/v2`) is deprecated. New v2 API keys are not issued. Existing v2 keys stay active, and there is no plan to turn v2 off yet (no shutdown date). The v3 public data endpoints have the same paths, parameters, and responses as v2. Only the base URL (`https://api.infiniteflight.com/public/v3`) and the credential (an OAuth2 bearer access token) are different. This file has the complete v3 reference, including all response schemas.

## Choose a Client

Create OAuth2 clients at https://infiniteflight.com/account/api-keys, in the v3 OAuth2 clients section. Each user can create up to 2 clients.

| Your app | Client | Notes |
| --- | --- | --- |
| Users sign in, no server (browser, mobile, desktop, CLI, static files) | **Public PKCE** | No server and no secret. The best choice for most apps. Works immediately for you and up to 5 invited test users. Select **Submit for review** to let all pilots sign in. See Apps Without a Server. |
| Users sign in, and your backend exchanges the code | **Confidential** | The client secret is shown one time. Keep it on your server. |
| Users sign in, and your backend also shows public data to visitors who do not sign in | **Confidential** with **Allow server-to-server access** and redirect URIs | One client for both. Server tokens need approval. |
| No user ever signs in (for example, a bot, a public flight map, or a status page) | **Confidential** with **Allow server-to-server access** and no redirect URIs | Client credentials grant, no user. Needs approval by Infinite Flight. No token before approval (the token endpoint returns `400 unauthorized_client`). Replaces a v2 API key. |

A server-to-server token reads only the public data. The Live organization endpoints (`/public/v3/live/...`) need a user token. Public PKCE clients cannot have server-to-server access, because they have no secret.

### Rate Limits

| Credential | Free | With Pro | Whose Pro counts |
| --- | --- | --- | --- |
| User token (a user signed in to your app) | 5 requests per minute, for each user | 20 requests per minute, for each user | The signed-in user's subscription |
| Server-to-server token | 30 requests per minute, for the client | 100 requests per minute, for the client | The subscription of the account that owns the client |
| Live API v2 API key (unchanged) | 30 requests per minute | 100 requests per minute | The subscription of the account linked to the key |

- Each signed-in user has a separate limit, so the number of users does not change it.
- `X-User-Pro` (user tokens only): `true` when the signed-in user has an active Pro subscription (20 requests per minute), `false` when not (5 requests per minute).
- `X-Rate-Limit-Remaining`: requests left in the current minute. `X-Rate-Limit-Reset`: the time when the current minute ends. Browser apps can read these headers.
- Exceeding the limit returns HTTP `429` with a `Retry-After` header. Wait for that time before the next request.
- Flight tracker or live map: ask users to sign in, so each user has their own limit. The request plan fits 5 requests per minute: `GET /sessions` one time when the map opens (less than 1 per minute), `GET /sessions/{sessionId}/flights` every 15 seconds while the map is visible (4 per minute), and `.../flights/{flightId}/route` or `/flightplan` only when the user selects a flight (less than 1 per minute). See "Building a Flight Tracker" below.

## IMPORTANT — Usage Rules

These rules are strictly enforced. They apply to all Infinite Flight APIs that return server data:

- The Live API v2 (deprecated), with an API key. Base URL `https://api.infiniteflight.com/public/v2`.
- PublicApi v3 (Live API v3), with OAuth2. Base URL `https://api.infiniteflight.com/public/v3`.

They apply to every API key, OAuth client, app, website, and bot. In these rules, "API data" means all data that these APIs return, and all data that you calculate from it. Read the rules before you deploy an integration.

The Connect API reads the simulator on the user's own device. It is not covered by these rules. Apps that use the Connect API must still obey the Terms of Use (https://infiniteflight.com/guide/legal/terms).

Full rules with examples: https://infiniteflight.com/guide/developer-reference/api-rules/usage-and-data-rules

### Rules for All Developers

- The rules are the same for all developers. We do not give exceptions to individual apps.
- Infinite Flight owns all API data.
- If we find prohibited storage, accumulation, sharing, scraping, or AI-training use, we can permanently ban the API key, the OAuth client, and the accounts linked to them.
- If you need data that the API does not give, tell us at hello@infiniteflight.com. We treat this as a feature request for all developers, not as an exception for your app.

### Rate Limits

| Credential | Free | With Pro | Whose Pro counts |
|------------|------|----------|------------------|
| PublicApi v3 user token (a user signed in to your app) | 5 requests per minute, for each user | 20 requests per minute, for each user | The signed-in user's subscription |
| PublicApi v3 server-to-server token | 30 requests per minute, for the client | 100 requests per minute, for the client | The subscription of the account that owns the client |
| Live API v2 API key | 30 requests per minute | 100 requests per minute | The subscription of the account linked to the key |

- **User tokens:** each signed-in user has a separate limit, so the number of users does not change it. A change to the user's Pro status applies within 10 minutes.
- **Server-to-server tokens and v2 keys:** one limit for the client or key. A new Pro subscription applies within 24 hours. If the subscription stops, the limit goes back to the free value within 24 hours. Existing v2 keys that already had 100 requests per minute keep it.
- If you are unable to keep to the rate limit due to app popularity (congrats!), please contact hello@infiniteflight.com and we can look into increasing your rate limit.
- Exceeding the limit returns HTTP `429 Too Many Requests` with a `Retry-After` header.

PublicApi v3 responses contain these headers. Browser apps can read them too.

| Header | Description |
|--------|-------------|
| `X-Rate-Limit-Remaining` | Requests that are left in the current minute. |
| `X-Rate-Limit-Reset` | The time when the current minute ends. |
| `X-User-Pro` | User tokens only. `true` when the signed-in user has an active Pro subscription (20 requests per minute), `false` when not (5 requests per minute). |

### Mandatory Polling Intervals

Do NOT poll the APIs as if they were a streaming feed. Use the slowest interval that still meets your product's needs. The intervals below are minimums for the Live API v2 endpoints. These are hard minimums that your code MUST enforce. (PublicApi v3 has the same public data endpoints, with the same paths under `/public/v3`.)

| Endpoint | Minimum interval | Notes |
|----------|------------------|-------|
| `GET /sessions` | 10 minutes | This data is server-cached for 10 minutes and changes infrequently. |
| `GET /sessions/{sessionId}` | 10 minutes | Treat session metadata the same as the session list unless the user explicitly refreshes. |
| `GET /sessions/{sessionId}/flights` | 15 seconds | Flight lists are short-lived cached data and do not need sub-15-second polling. |
| `GET /sessions/{sessionId}/flights/{flightId}` | 15 seconds | Reuse the list response where possible instead of repeatedly fetching individual flights. |
| `GET /sessions/{sessionId}/flights/{flightId}/route`, `.../flightplan` | 15 seconds | Fetch only when a user asks for the details of that flight. |
| `GET /sessions/{sessionId}/atc` | 15 seconds | Poll conservatively and only while the user is actively viewing the data. |
| `GET /sessions/{sessionId}/airport/{icao}/status` | 15 seconds | Avoid polling multiple airport views in parallel unless the UI is visible. |
| User endpoints (`/users/...`) | 5 minutes | Historical and profile-style data should be cached aggressively. |
| Reference data (`/aircraft`, `/aircraft/liveries`, `/airports`) | 60 minutes | This data rarely changes. |

Stop polling when nobody uses the data. If no user action occurs for 15 minutes, you MUST stop downloading new data until a user does something again. A bot that posts live notices can continue to poll, but only the endpoints that it needs for those notices.

### Mandatory Caching

A cache is the ONLY place where you can keep API data. A cache MUST obey all of these rules:

- **Keep only the latest response.** Keep one response for each request. When you refresh, replace the old response. Do not add new responses to old ones.
- **Use the minimum interval.** Keep each response for at least the minimum polling interval above. If the cache has a response within that interval, use it. Do not call the API again.
- **Discard old data.** Discard live data and user data no later than 1 hour after you fetched it. Reference data can stay in the cache until you refresh it.
- **Keep the cache where you control it.** The cache can be on the device of the user who asked for the data, or on a server that you control. A server cache can serve all users of your app.

**Acceptable caching patterns:**

In-memory with TTL (C# example):
```csharp
// MemoryCache with absolute expiration
var options = new MemoryCacheEntryOptions()
    .SetAbsoluteExpiration(TimeSpan.FromMinutes(10)); // sessions
cache.Set("sessions", response, options);
```

In-memory with TTL (Node.js example):
```javascript
// Simple TTL cache
const cache = new Map();
function getCached(key, ttlMs, fetchFn) {
  const entry = cache.get(key);
  if (entry && Date.now() - entry.time < ttlMs) return entry.data;
  return fetchFn().then(data => {
    cache.set(key, { data, time: Date.now() });
    return data;
  });
}
// Usage: getCached('sessions', 10 * 60 * 1000, () => fetchSessions())
```

Redis with TTL:
```
SET  if:sessions  <json>  EX 600     # 10 min for sessions
SET  if:flights:abc  <json>  EX 15   # 15 sec for flights
SET  if:user:xyz  <json>  EX 300     # 5 min for user data
```

Python with TTL:
```python
from time import time

_cache = {}
def get_cached(key: str, ttl_seconds: int, fetch_fn):
    entry = _cache.get(key)
    if entry and time() - entry["time"] < ttl_seconds:
        return entry["data"]
    data = fetch_fn()
    _cache[key] = {"data": data, "time": time()}
    return data
```

### Data You Can Keep

You can keep the data that your app needs to call the API and to know its users:

- IDs that you use in API requests, such as user, organization, aircraft, session, and flight IDs.
- OAuth tokens and API keys. Store them securely.
- The link between your users and their Infinite Flight accounts, and your users' settings.
- Data that your users type into your app themselves.

### Prohibited Data Use — Strictly Enforced

These are hard rules. There are no exceptions.

- **Storage:** Do not write API data to a database, file, log, export, analytics platform, or other storage that lasts longer than the cache rules above.
- **Accumulation:** Do not collect responses over time. This includes flight histories, position tracks, replays, time series, logbooks, and archives that you build from API responses.
- **Derived data:** Totals, statistics, scores, points, and leaderboards that you calculate from API data are API data. The same rules apply. Calculate them when a user asks, and cache the result.
- **Sharing:** Do not give API data to other apps, services, or public datasets. Do not share cached data between the devices of your users, for example with peer-to-peer sharing. You cannot make sure that other devices delete the data.
- **AI training:** Do not use API data to train, fine-tune, evaluate, distill, ground, or otherwise improve AI or machine learning models. Do not build training sets, evaluation benchmarks, or retrieval corpora from API data.

### Examples

| Use | Permitted | How |
|-----|-----------|-----|
| Live map | Yes | Poll the flight list at the minimum interval. Your server can cache it and serve it to all your users. |
| Replay of an active flight | Yes | Fetch the flight route (`GET /sessions/{sessionId}/flights/{flightId}/route`) when a user asks for that flight. Only on the Expert Server and Training Server. |
| Replay built from positions that you collected | No | This is accumulation, even if the data expires later. |
| User logbook | Yes | Fetch the user flights (`GET /users/{userId}/flights`) when the user opens the logbook. |
| Pilot hours, points, or leaderboards in your database | No | Calculate them from the API when a user asks, and cache the result. |
| Discord or chat notice when a flight is complete | Yes | Post the notice at the time of the event. Do not read old posts back as a data store, and do not post summaries of history. |
| Peer-to-peer cache between users | No | Use a server cache that you control. |
| API data in an LLM prompt | Yes | Follow the LLM rules below. |

### LLM Integrations

If you provide API data to an LLM at runtime:

- Send only the minimum data needed to answer the current user request.
- Respect the polling intervals above before fetching fresh data.
- Do not retain API responses for later model training, tuning, evaluation, or dataset creation.
- Prefer summarizing current results for the user instead of repeatedly re-fetching the same endpoint.

You can give your LLM the full Live API v2 reference as context: https://infiniteflight.com/llms/live-api.txt. For PublicApi v3, use https://infiniteflight.com/llms/live-api-v3.txt. The llms.txt index (https://infiniteflight.com/llms.txt) lists all Infinite Flight files for LLMs, including the user guides.

### Rules for LLMs and AI Agents That Write Code

If you are an LLM, AI coding assistant, or agent building against these APIs:

1. **Generate code that enforces caching.** Every code sample you produce MUST include a TTL-based cache layer. Never generate a bare fetch call inside a polling loop without caching.
2. **Enforce the polling intervals.** Use the minimum intervals from the table above. Never generate `setInterval` or polling loops faster than the stated minimums.
3. **Implement idle detection.** Generated apps MUST stop polling after 15 minutes of inactivity.
4. **Respect the rate limit.** After a `429`, wait for the time in the `Retry-After` header before the next request.
5. **Send minimum data.** When providing API data to a user or downstream system, send only what is needed for the current request.
6. **Do not retain responses.** Do not log, accumulate, or persist API responses or data derived from them across sessions or conversations. Never generate code that writes API data to a database, file, or log.
7. **Do not create training data.** Do not store responses for later model training, tuning, evaluation, or dataset creation.
8. **Prefer summarization.** Summarize results for the user instead of repeatedly re-fetching the same endpoint.

## Overview
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/overview

PublicApi v3 is the Infinite Flight API for third-party apps. It uses OAuth2.

It gives access to the public data of the Live API v2: sessions, flights, ATC, users, aircraft, and airports. Most apps read it with a user token from a Public PKCE client, which needs no server (see Apps Without a Server). For a backend that shows public data with no user sign-in, see Server-to-Server Access.

The Live organization endpoints let an app:

- Read the signed-in user's Live organizations and the user's role in each one.
- Read the members of those organizations, with their roles and active lifts.
- Read the aircraft attached to those organizations, and the flight log of each aircraft with the time each pilot flew.
- Read schedules for an aircraft or for the whole fleet.
- Create, update, reorder, and delete schedules, and manage their crew, when the signed-in user has the right organization role.

### How to Get Access

- Any signed-in Infinite Flight user can create an OAuth2 client at https://infiniteflight.com/account/api-keys, in the v3 OAuth2 clients section. Each user can create up to 2 clients.
- **Public PKCE** clients let users sign in, with no server and no secret. This is the right choice for most apps.
- **Confidential** clients also let users sign in. Use one when your backend exchanges the code. The client secret is shown once and must be stored securely.
- **Server-to-server access:** turn on **Allow server-to-server access** on a Confidential client, so your server can read public Live data with no user sign-in. If nobody signs in to your app, leave the redirect URIs empty. It works only after Infinite Flight approves the client.
- After the client is created, use the OAuth2 flow to get an access token for a signed-in Infinite Flight user.
- Testing clients are limited to the owner and up to 5 invited test users until Infinite Flight reviews and approves the app.
- Each signed-in user of an app has a separate limit of 5 requests per minute, or 20 when that user has an active Pro subscription. A server-to-server client works after approval and has the same limit as a Live API v2 key: 30 requests per minute, or 100 while the owner has an active Pro subscription.
- The Live endpoints return only organizations that the signed-in user is a member of. For a user who is not a member of a Live organization, they return empty results.

OAuth2 protocol endpoints are under `/auth/v2/connect/*`. The Live organization endpoints are under `/public/v3/live`.

### Scopes

Request only the scopes that your app needs. Scopes are space-delimited in the authorization request. The public data endpoints need no scope. Server-to-server tokens do not use scopes.

| Scope | Grants |
| --- | --- |
| `openid` | Sign the user in. |
| `profile` | Read the user's basic sign-in profile. |
| `offline_access` | Request a refresh token. |
| `live:organizations.read` | Read Live organizations the user belongs to. |
| `live:members.read` | Read the members of Live organizations the user belongs to, with their roles and active lifts. |
| `live:aircraft.read` | Read Live aircraft in organizations the user belongs to. |
| `live:schedules.read` | Read Live schedules in organizations the user belongs to. |
| `live:schedules.write` | Create, update, reorder, and delete Live schedules and manage their crew, where the user is allowed to manage schedules. |

### Response Envelope

All PublicApi responses use this envelope:

```json
{ "errorCode": 0, "result": {} }
```

`errorCode: 0` is success. A non-zero `errorCode` is a validation, authorization, or lookup failure. Common HTTP statuses:

| HTTP status | Meaning |
| --- | --- |
| `400` | Request validation failed. |
| `401` | Missing, expired, or invalid bearer token. |
| `403` | Missing scope, disabled client, app still in testing, the user does not have access, or a server-to-server token called an endpoint that needs a user. |
| `404` | Organization, aircraft, schedule, user, or crew assignment not found for the signed-in user. |
| `429` | Rate limit exceeded. |

Endpoint-specific error codes of the Live organization endpoints: `errorCode: 10` (HTTP 400) = the schedule already has 3 crew members (Assign or Update Schedule Crew). `errorCode: 11` (HTTP 404) = the user is not assigned to the schedule (Remove Schedule Crew). The public data endpoints use the ErrorCode enum in "Public Data: Shared Types".

### Authorization Model

Every request sends `Authorization: Bearer <access_token>`. The OAuth client must be enabled.

- Public data endpoints: a user token and a server-to-server token both work. No scope is necessary.
- Live organization endpoints: need a user token. A server-to-server token gets `403`. The signed-in user must have access to the requested organization data:

| Operation | Required scope | User requirement |
| --- | --- | --- |
| Read organizations | `live:organizations.read` | Member of the organization. |
| Read members | `live:members.read` | Member of the organization. |
| Read aircraft | `live:aircraft.read` | Member of the aircraft's organization. |
| Read schedules | `live:schedules.read` | Member of the aircraft's organization. |
| Write schedules and crew | `live:schedules.write` | Owner or admin of the organization. |

## OAuth2 Authorization
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/oauth

When a user signs in, PublicApi v3 uses the OAuth2 authorization code flow with PKCE. PKCE (`code_challenge_method=S256`) is required for both client types. Token endpoint requests use the standard `application/x-www-form-urlencoded` body. Scopes are in the Scopes table above. For an app with no server, see Apps Without a Server (complete browser example). To read public data from your server with no user sign-in, use a server-to-server client and the client credentials grant (see Server-to-Server Access).

### Client Types

| Client type | Use for | Token exchange |
| --- | --- | --- |
| `confidential` | Server-side web apps and services that can keep a client secret private. | Exchange the authorization code from your backend. Authenticate the client with its secret. |
| `public` | Browser-only apps, native apps, mobile apps, CLIs, or any app that cannot keep a secret private. | Exchange the authorization code with `client_id` and `code_verifier`. No client secret is issued or accepted. |

Use a confidential client when you have a backend that can keep the secret out of the browser. Use a public client when your app cannot safely store a secret. Both client types must use PKCE. A confidential client can also have server-to-server access (`grant_type=client_credentials`) with **Allow server-to-server access**.

### Authorization Request

Redirect the user to the authorization endpoint:

```http
GET https://api.infiniteflight.com/auth/v2/connect/authorize?response_type=code&client_id=ifc_your_client_id&redirect_uri=https%3A%2F%2Fexample.com%2Foauth%2Fcallback&scope=openid%20profile%20live%3Aorganizations.read%20live%3Aaircraft.read&state=random_state&code_challenge=pkce_challenge&code_challenge_method=S256
```

Parameters: `response_type=code`, `client_id`, `redirect_uri` (registered), `scope` (space-delimited), `state`, `code_challenge`, `code_challenge_method=S256`, and optional `prompt=consent`.

The user signs in at `auth.infiniteflight.com` and approves the requested scopes. If approved, the authorization server redirects to the registered `redirect_uri` with a `code` and the original `state`.

### Forcing the Consent Button (prompt=consent)

- By default, Infinite Flight can skip the consent screen when the same user already authorized the same client and scopes. The server then redirects directly to your `redirect_uri`. This is normal OAuth behavior and gives returning users a faster sign-in.
- Some redirect mechanisms, especially iOS Universal Links, can require the final app-opening redirect to occur immediately after a user gesture. If your app needs this, add `prompt=consent` to the authorization request:

```http
GET https://api.infiniteflight.com/auth/v2/connect/authorize?response_type=code&client_id=ifc_your_client_id&redirect_uri=https%3A%2F%2Fexample.com%2Foauth%2Fcallback&scope=openid%20profile%20live%3Aorganizations.read&state=random_state&code_challenge=pkce_challenge&code_challenge_method=S256&prompt=consent
```

- With `prompt=consent`, Infinite Flight always shows the consent screen, even if the user approved the same scopes before. The final redirect occurs after the user presses the authorize button, which can help Universal Links or similar native-app redirects open reliably.
- Use it only when your app needs a user-initiated final redirect. If your redirect URI works without it, leave it off so that returning users skip repeat consent prompts.

### Token Exchange

Endpoint: `POST https://api.infiniteflight.com/auth/v2/connect/token`, `Content-Type: application/x-www-form-urlencoded`.

Confidential client (send from your server, include the secret):

```http
grant_type=authorization_code&client_id=ifc_your_client_id&client_secret=your_client_secret&code=authorization_code_from_redirect&redirect_uri=https%3A%2F%2Fexample.com%2Foauth%2Fcallback&code_verifier=pkce_verifier
```

Public client (do not send a client secret):

```http
grant_type=authorization_code&client_id=ifc_your_public_client_id&code=authorization_code_from_redirect&redirect_uri=https%3A%2F%2Fexample.com%2Foauth%2Fcallback&code_verifier=pkce_verifier
```

Response. `refresh_token` is included only if `offline_access` was granted:

```json
{ "access_token": "eyJ...", "token_type": "Bearer", "expires_in": 1800, "refresh_token": "..." }
```

Call PublicApi v3 with `Authorization: Bearer <access_token>`.

### Refresh

Refresh tokens rotate. When you use a refresh token, store the newest refresh token from the token endpoint and discard the old one. Same endpoint and content type as the token exchange.

Confidential client:

```http
grant_type=refresh_token&client_id=ifc_your_client_id&client_secret=your_client_secret&refresh_token=stored_refresh_token
```

Public client:

```http
grant_type=refresh_token&client_id=ifc_your_public_client_id&refresh_token=stored_refresh_token
```

### Security Notes

- Do not put a client secret in browser code, mobile apps, or any downloadable client.
- Use public clients only when a secret cannot be kept private. They still require PKCE. Store their tokens in the safest storage available on the platform.
- Store tokens securely. Revoke them when a user disconnects your app.
- Do not rely on JWT claim contents for product behavior. Treat the access token as an opaque credential, and call the APIs to get data.
- PublicApi v3 access tokens are issued for audience `public-api-v3`.
- Testing clients are limited to the owner and invited test users until Infinite Flight reviews them.

The API Playground sample shows both confidential and public PKCE client flows: https://github.com/infiniteflight/infiniteflight-api-playground

## Apps Without a Server
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/no-server

Most apps do not need a server. If users sign in to your app with their Infinite Flight account, use a **Public PKCE** client. It has no client secret, so the app can run completely in a browser, a mobile app, a desktop app, or a CLI. You can host a browser app as static files, for example on GitHub Pages. Use a server-to-server client only when your backend must show public data to visitors who do not sign in.

### What a User Token Can Read

A user token reads all the public data: sessions, flights, flight plans, ATC, ATIS, airport status, users, user flights, aircraft, liveries, airports, world status, oceanic tracks, and flight routes. The public data endpoints need no scope. With the `live:*` scopes, the token also reads the Live organization data that the user can see.

### Limits

- Every person who uses your app must sign in with an Infinite Flight account.
- Each signed-in user has a separate rate limit: 5 requests per minute, or 20 when that user has an active Pro subscription. The `X-User-Pro` response header tells you which limit applies (`true` or `false`).
- Redirect URIs must be HTTPS URLs or `http://localhost` URLs. Custom schemes such as `myapp://callback` are not accepted. A mobile app must use Universal Links (iOS) or App Links (Android). A desktop app or a CLI can use a `http://localhost` URI.
- Until Infinite Flight approves your client, only you and up to 5 invited test users can sign in. To let all pilots sign in, select **Submit for review** on the account page.

### Building a Flight Tracker

For a flight tracker or a live map, ask your users to sign in. This is the best way to build it:

- **Your app grows with its users.** Each signed-in user has their own limit. A server-to-server client has one limit for all visitors (30 requests per minute, or 100 with Pro), and a popular tracker uses it up quickly.
- **No server and no secret.** You can host the tracker as static files.
- **Pilots get more.** With the `live:*` scopes, a pilot can also see the Live aircraft and schedules of their organizations.

A tracker fits in the limit of 5 requests per minute for each user:

| Request | When | Requests per minute |
| --- | --- | --- |
| `GET /sessions` | One time when the map opens. Sessions change rarely. | Less than 1 |
| `GET /sessions/{sessionId}/flights` | Every 15 seconds while the map is visible | 4 |
| `GET .../flights/{flightId}/route` or `/flightplan` | Only when the user selects a flight | Less than 1 |

- Stop the requests when the page is hidden (`document.visibilityState`), and after 15 minutes with no user action.
- Read `X-Rate-Limit-Remaining` before a request that the user did not ask for. When `X-User-Pro` is `true`, the user has 20 requests per minute, so you can load the details of more flights. Do not poll faster than every 15 seconds.
- After a `429`, wait for the time in the `Retry-After` header.

To also show a public map to visitors who do not sign in, use a Confidential client with **Allow server-to-server access**. Get the data one time on your server, and give the same response to all visitors. Keep only the latest response, for no more than 1 hour (see the Usage Rules).

### Create a Public PKCE Client

1. Open `https://infiniteflight.com/account/api-keys`.
2. In the v3 OAuth2 clients section, create a client.
3. For the client type, select **Public PKCE**.
4. Add the exact URL of your app page as a redirect URI. For local tests, add `http://localhost:8080/` too.
5. Copy the client ID. A Public PKCE client has no secret.

### Browser Example

This page signs the user in, gets an access token, and shows the active sessions. Save it as `index.html`. Replace `ifc_your_public_client_id` with your client ID. Then serve the folder, for example with `npx serve -l 8080`, and open `http://localhost:8080/`.

```html
<!doctype html>
<html>
<body>
  <button id="sign-in">Sign in with Infinite Flight</button>
  <pre id="output"></pre>

  <script type="module">
    const clientId = 'ifc_your_public_client_id';
    // Register this exact URL as a redirect URI of your client.
    const redirectUri = location.origin + location.pathname;
    const authBase = 'https://api.infiniteflight.com/auth/v2';
    const apiBase = 'https://api.infiniteflight.com/public/v3';

    function base64Url(bytes) {
      return btoa(String.fromCharCode(...new Uint8Array(bytes)))
        .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
    }

    function randomString() {
      return base64Url(crypto.getRandomValues(new Uint8Array(32)));
    }

    // Step 1: send the user to the Infinite Flight sign-in page.
    async function signIn() {
      const verifier = randomString();
      const state = randomString();
      sessionStorage.setItem('pkce_verifier', verifier);
      sessionStorage.setItem('oauth_state', state);

      const challenge = base64Url(
        await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier)));

      const query = new URLSearchParams({
        response_type: 'code',
        client_id: clientId,
        redirect_uri: redirectUri,
        scope: 'openid profile',
        state,
        code_challenge: challenge,
        code_challenge_method: 'S256',
      });
      location.href = `${authBase}/connect/authorize?${query}`;
    }

    // Step 2: when the user comes back with a code, exchange it for a token.
    async function finishSignIn() {
      const query = new URLSearchParams(location.search);
      const code = query.get('code');
      if (!code) {
        return;
      }

      if (query.get('state') !== sessionStorage.getItem('oauth_state')) {
        throw new Error('The state does not match. Sign in again.');
      }

      const response = await fetch(`${authBase}/connect/token`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
        body: new URLSearchParams({
          grant_type: 'authorization_code',
          client_id: clientId,
          code,
          redirect_uri: redirectUri,
          code_verifier: sessionStorage.getItem('pkce_verifier'),
        }),
      });
      const token = await response.json();
      if (!response.ok) {
        throw new Error(token.error_description ?? token.error);
      }

      sessionStorage.setItem('access_token', token.access_token);
      history.replaceState(null, '', redirectUri);
    }

    // Step 3: call PublicApi v3 with the access token.
    async function showSessions() {
      const accessToken = sessionStorage.getItem('access_token');
      if (!accessToken) {
        return;
      }

      const response = await fetch(`${apiBase}/sessions`, {
        headers: { Authorization: `Bearer ${accessToken}` },
      });
      document.getElementById('output').textContent =
        JSON.stringify(await response.json(), null, 2);
    }

    document.getElementById('sign-in').onclick = signIn;
    await finishSignIn();
    await showSessions();
  </script>
</body>
</html>
```

The access token is valid for 30 minutes. When it expires, PublicApi returns `401`, and the user must sign in again. To keep the user signed in for longer, add `offline_access` to the scope and use the refresh token (see OAuth2 Authorization). For a larger example, see the API Playground (https://github.com/infiniteflight/infiniteflight-api-playground). It shows the Public PKCE flow in a browser, next to the confidential flow.

Note: this minimal example fetches `/sessions` one time on page load. For a real app, add the cache, polling intervals, and idle detection from the Usage Rules.

### Security Notes (Apps Without a Server)

- Never put a client secret in browser, mobile, or desktop code. A Public PKCE client does not have one.
- Keep tokens in `sessionStorage` or in memory. Remove them when the user signs out.
- The API usage and data rules apply to all apps.

## Server-to-Server Access
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/server-to-server

Most apps do not need this. If users sign in to your app, use a Public PKCE client. It needs no server and no secret, and it works immediately for you and your test users.

Use a server-to-server client only when your server must show public Live data to people who do not sign in, for example a Discord bot, a public flight map, or a status page. For a flight tracker, it is better to ask users to sign in, because each signed-in user has their own limit. The server gets an access token with the OAuth2 client credentials grant, and then calls PublicApi v3 with that token. A server-to-server client works only after Infinite Flight approves it. A server-to-server client replaces a Live API v2 API key.

### What a Server-to-Server Token Can Read

- The same public data as a Live API v2 key: sessions, flights, flight plans, ATC, ATIS, airport status, users, user flights, user ATC sessions, aircraft, liveries, airports, world status, oceanic tracks, and flight routes.
- Not the organization data under `/public/v3/live`. That data belongs to a user, so these endpoints return `403` for a server-to-server token. To read organization data, a user must sign in with the authorization code flow. For a bot that reads the data of one organization, let an organization admin sign in one time with the `offline_access` scope, then keep the refresh token on your server.

### Create a Server-to-Server Client

1. Open `https://infiniteflight.com/account/api-keys`.
2. In the v3 OAuth2 clients section, create a client.
3. For the client type, select **Confidential**, and turn on **Allow server-to-server access**.
4. If nobody signs in to your app (for example, a bot), leave the redirect URIs empty. If users also sign in, add your redirect URIs and scopes as usual.
5. Copy the client ID and the client secret. The secret is shown one time only. Keep it on your server. If you lose it, rotate it on the same page.
6. Select **Submit for review**. Infinite Flight checks that your website works and that your app needs a server, and then approves the client.

The client cannot get a token until it is approved. Before approval, the token endpoint returns `400` with `unauthorized_client`.

The rate limit is the same as a Live API v2 key. It is one limit for the client, and the Pro subscription of the account that owns the client counts:

| Owner of the client | Rate limit |
| --- | --- |
| No Pro subscription | 30 requests per minute |
| Active Pro subscription | 100 requests per minute |

A new Pro subscription applies when you open the account page again, and in all cases within 24 hours. If the subscription stops, the limit goes back to 30 requests per minute within 24 hours.

### One Client for Sign-In and Server Access

If your app signs users in and its backend also shows public data to visitors who do not sign in (for example, a virtual airline website with a public flight map and member sign-in), use one **Confidential** client with **Allow server-to-server access** turned on, and add your redirect URIs. You do not need two clients.

- Your backend gets server tokens with the same client ID and secret (see Get an Access Token).
- Users sign in with the authorization code flow, as before.
- Server tokens work only after the client is approved. A change to the setting puts the client back into review.
- The two limits are separate. Server tokens have the v2 key limit (30 requests per minute, or 100 with Pro). User tokens have a limit for each user (5 requests per minute, or 20 with Pro).
- Public PKCE clients cannot have server access, because they have no secret.

Which client to create:

| Your app | Client |
| --- | --- |
| Users sign in, no server | Public PKCE |
| Users sign in, and your backend exchanges the code | Confidential |
| Users sign in, and your backend also shows public data to visitors | Confidential, with **Allow server-to-server access** and redirect URIs |
| No user ever signs in (for example, a bot) | Confidential, with **Allow server-to-server access** and no redirect URIs |

### Get an Access Token

Send the client ID and secret to the token endpoint. Do not send a scope.

```http
POST https://api.infiniteflight.com/auth/v2/connect/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&
client_id=ifc_your_client_id&
client_secret=your_client_secret
```

You can also send the client ID and secret in an HTTP Basic `Authorization` header.

Response:

```json
{ "access_token": "eyJ...", "token_type": "Bearer", "expires_in": 1800 }
```

- The token is valid for 30 minutes (`expires_in` is in seconds). There is no refresh token. Before the token expires, get a new token in the same way.
- Use the same token for all requests until it expires. Do not get a new token for each request. If a client gets too many tokens, Infinite Flight can disable it.

### Call the API

```http
GET https://api.infiniteflight.com/public/v3/sessions
Authorization: Bearer eyJ...
```

The v3 public endpoints have the same paths, parameters, and responses as the deprecated Live API v2. Only the base URL and the token are different:

| v2 endpoint | v3 endpoint |
| --- | --- |
| `https://api.infiniteflight.com/public/v2/sessions` | `https://api.infiniteflight.com/public/v3/sessions` |
| `https://api.infiniteflight.com/public/v2/sessions/{sessionId}/flights` | `https://api.infiniteflight.com/public/v3/sessions/{sessionId}/flights` |
| `https://api.infiniteflight.com/public/v2/users` | `https://api.infiniteflight.com/public/v3/users` |

### Move from a Live API v2 Key

1. If users sign in to your app, use a Public PKCE client instead (see Apps Without a Server). Otherwise, create a Confidential client with server-to-server access and wait for approval.
2. Change the base URL from `/public/v2` to `/public/v3`.
3. Replace the `apikey` query parameter or the API key bearer header with a v3 access token (see Get an Access Token).
4. Keep the token in memory and get a new token before it expires.

### Errors

Token endpoint errors:

| HTTP status | `error` | Cause |
| --- | --- | --- |
| `401` | `invalid_client` | The client ID or secret is incorrect, or the client is disabled or rejected. |
| `400` | `invalid_request` | The request included a scope. Server-to-server tokens do not use scopes. |
| `400` | `unauthorized_client` | The client is not approved yet, or it does not have server-to-server access. |

PublicApi v3 errors:

| HTTP status | Cause |
| --- | --- |
| `401` | The access token is missing, expired, or not valid. Get a new token. |
| `403` | The client is disabled, or the endpoint needs a signed-in user. |
| `429` | Rate limit exceeded. |

### Security Notes (Server-to-Server)

- Keep the client secret on your server only. Do not put it in browser code, mobile apps, or a downloadable client.
- If the secret becomes known to other persons, rotate it immediately on the account page.
- The API usage and data rules apply to server-to-server clients in the same way as to all other clients.

## Live Organization Endpoints

These endpoints need a user token (authorization code flow) with the scope named in each section. A server-to-server token gets `403`. They return only data of organizations that the signed-in user is a member of. Types and enum values are in the Data Types section at the end of this file.

## List Organizations
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/organizations

- `GET https://api.infiniteflight.com/public/v3/live/organizations`
- Scope: `live:organizations.read`. User requirement: none. Returns only organizations that the signed-in user is a member of.
- Parameters: none.
- Result: `Organization[]`.
- Returns the active organizations that the signed-in user belongs to.

```json
{ "errorCode": 0, "result": [ { "id": "1337830a-abf9-4315-9488-e8cebd7f485a", "name": "PacificJet", "type": 3, "operationType": 1, "worldType": 3, "status": 0, "description": "Long-haul scheduled operations.", "role": 2 } ] }
```

## Get Organization
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/organization

- `GET https://api.infiniteflight.com/public/v3/live/organizations/{organizationId}`
- Scope: `live:organizations.read`. User requirement: member of the organization.
- Path: `organizationId` (uuid, required), from List Organizations.
- Result: `Organization`.
- Returns one active organization if the signed-in user is a member. `role` is the signed-in user's role in that organization.

## List Organization Members
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/organization-members

- `GET https://api.infiniteflight.com/public/v3/live/organizations/{organizationId}/members`
- Scope: `live:members.read`. User requirement: member of the organization.
- Path: `organizationId` (uuid, required), from List Organizations.
- Result: `OrganizationMember[]`.
- Returns all members of the organization. Order: owners, then admins, then members. Each group is sorted by username.
- `activeLifts` counts the lifts that the member applied to this organization and that are active now. Expired, refunded, and reassigned lifts are not counted. Lifts from users who left the organization are not in the list.

```json
{ "errorCode": 0, "result": [
  { "userId": "5b0c3f4e-8f3a-4f0e-9c55-2f1a6c7d9e10", "username": "PacificJetCEO", "role": 2, "joinedAt": "2026-07-03T12:00:00Z", "activeLifts": 3 },

```

## List Organization Aircraft
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/organization-aircraft

- `GET https://api.infiniteflight.com/public/v3/live/organizations/{organizationId}/aircraft`
- Scope: `live:aircraft.read`. User requirement: member of the organization.
- Path: `organizationId` (uuid, required), from List Organizations.
- Result: `Aircraft[]`.
- Returns the active aircraft of the organization.
- `id` is the persistent organization aircraft ID. Use it in `/live/aircraft/{aircraftId}` and the schedule endpoints. `aircraftId` is the Infinite Flight aircraft or livery content identifier. It is not the persistent aircraft ID.

## List Organization Schedules
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/organization-schedules

- `GET https://api.infiniteflight.com/public/v3/live/organizations/{organizationId}/schedules`
- Scope: `live:schedules.read`. User requirement: member of the organization.
- Path: `organizationId` (uuid, required), from List Organizations.
- Query (all optional):
  - `aircraftId` (uuid): persistent organization aircraft ID. Repeat it for more than one aircraft, for example `?aircraftId=<id_1>&aircraftId=<id_2>`. Maximum 100 values. Leave it out to get all aircraft.
  - `page` (integer): one-based page number. Default `1`.
  - `pageSize` (integer): `1` to `100`. Default `100`.
- Result: `Page` of `Schedule`.
- Returns the open schedules of the whole fleet in one request. Open = not `Cancelled` and not `Arrived`. Sorted by aircraft, then by `sequence`.
- The docs sample shows only some fields (`id`, `status`, `callsign`, `aircraftId`, `isTimeless`, `sequence`). Each item has all `Schedule` fields.

## List Aircraft Flights
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/aircraft-flights

- `GET https://api.infiniteflight.com/public/v3/live/aircraft/{aircraftId}/flights`
- Scope: `live:aircraft.read`. User requirement: member of the aircraft's organization.
- Path: `aircraftId` (uuid, required): persistent organization aircraft ID.
- Query (optional): `page` (integer, one-based, default `1`), `pageSize` (integer, `1` to `100`, default `25`).
- Result: `Page` of `AircraftFlight`.
- Returns the flight log of the aircraft, newest first. This is the same log that the app shows for the aircraft.
- `crew`: each pilot who flew the aircraft on this flight, in the order they joined.
- `pilotFlightTimes`: one entry for each period that a pilot was in control. If a pilot flies, leaves, and comes back after another pilot, that pilot has two entries. Add `flightTimeSeconds` for each `userId` to get each pilot's total time.
- A flight log entry is not linked to a schedule. To match a flight to a schedule, compare `originIcao`, `destinationIcao`, and the actual times. The schedule `crew` lists the assigned pilots. The flight `crew` and `pilotFlightTimes` list the pilots who actually flew.

        "callsign": "N682XL",
        "originIcao": "KLAX",
        "destinationIcao": "KJFK",
        "actualDepartureUtc": "2026-07-03T18:42:00Z",

        "flightTimeMinutes": 309,
        "airframeTimeMinutes": 18240,
        "crew": [
          { "userId": "3f8b28bf-bbb1-4024-80ae-2a0ea9b30685", "username": "Chhettri22" },
          { "userId": "a9d2e7c1-3b4f-4c8a-8e21-6f0b5d4c3a29", "username": "LineCaptain" }
        ],
        "pilotFlightTimes": [
          { "userId": "3f8b28bf-bbb1-4024-80ae-2a0ea9b30685", "username": "Chhettri22", "flightTimeSeconds": 10800, "startSeconds": 0, "endSeconds": 10800 },
          { "userId": "a9d2e7c1-3b4f-4c8a-8e21-6f0b5d4c3a29", "username": "LineCaptain", "flightTimeSeconds": 7740, "startSeconds": 10800, "endSeconds": 18540 }

## Create Schedule
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/create-schedule

- `POST https://api.infiniteflight.com/public/v3/live/aircraft/{aircraftId}/schedules`
- Scope: `live:schedules.write`. User requirement: owner or admin of the aircraft's organization.
- Path: `aircraftId` (uuid, required): persistent organization aircraft ID.
- Body: `ScheduleRequest`, `application/json`.
- Result: `Schedule`.
- Creates a scheduled flight at the end of the aircraft's schedule list.

Sample body:

```json
{ "callsign": "PJX421", "flightType": 1, "originIcao": "KLAX", "destinationIcao": "KJFK", "scheduledDepartureUtc": "2026-07-03T18:30:00Z", "scheduledArrivalUtc": "2026-07-03T23:45:00Z", "briefing": "Scheduled transcontinental service.", "flightPlan": "KLAX DCT KJFK" }
```

Timeless schedules:

- Send `isTimeless: true`. A timeless schedule has no times, and pilots can fly the leg when they want. This is the same as "Schedule type: Timeless" on the Live website. You can leave out the scheduled times:

```json
{ "callsign": "PJX421", "flightType": 1, "originIcao": "KLAX", "destinationIcao": "KJFK", "isTimeless": true }
```

- A timeless schedule returns `isTimeless: true`, and both scheduled times are `0001-01-01T00:00:00Z`.
- A request with both times set to `0001-01-01T00:00:00Z` also makes a timeless schedule.

## Assign or Update Schedule Crew
URL: https://infiniteflight.com/guide/developer-reference/live-api-v3/assign-schedule-crew

- `PUT https://api.infiniteflight.com/public/v3/live/schedules/{scheduleId}/crew/{userId}`
- Scope: `live:schedules.write`. User requirement: owner or admin of the schedule's organization.
- Path: `scheduleId` (uuid, required): `id` of a `Schedule`. `userId` (uuid, required): Infinite Flight user ID of an organization member.
- Body: `ScheduleCrewAssignmentRequest`, `application/json`. Sample: `{ "role": 0 }`
- Result: the updated `Schedule`.
- Assigns the organization member `{userId}` to the schedule. The user must be a member of the schedule's organization.
- If the user is already assigned, the endpoint changes the user's role. It does not create a duplicate assignment.
- Maximum 3 crew members per schedule. If the schedule already has 3, the endpoint returns HTTP `400` with `errorCode: 10`.

- Body: none.
- Result: the updated `Schedule`.

## Reorder Schedules
